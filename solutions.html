Wiom TV × Booking · Solution options

Bring the user back to Wiom TV — without losing the booking

A user hits the unserviceable screen, tries Wiom TV, then quits. On relaunch they land on “check my area” with no way back to Wiom TV. Solve the repeat‑access problem and give them a fair, objective‑1 chance to book.

🎯 The problem

Wiom TV lives only on the unserviceable screen. It isn’t saved to the app’s booking history, and the user didn’t add wiom.tv to their home screen — so the Wiom app is their only door back, and it opens on “enter location.”

🔑 The unlock

The screen they land on is already the booking funnel. Objective 1 is served by default. So this isn’t a tug‑of‑war — we just add a Wiom TV re‑entry and make the landing smart about the fact they were unserviceable.

  • Location was mis‑detected → let them re‑check
  • They moved → new address, new check
  • Wiom expanded coverage → their area may now be serviceable

Tech options · leanest first · reuse existing infra

T1

Local flag only

0 backend~20–30 LOC

Stamp lastUnserviceable {ts, lat, lng, address} in shared_preferences on the unserviceable screen. On locationHome, if present & fresh, render a Wiom TV re‑entry + a pre‑filled “re‑check” shortcut. Clear on a successful booking.

Leanest possible first cut.

✓ Recommended core T2

Flag + auto re‑check

0 new backend~40–60 LOC

Same flag, but on return silently re‑run the existing serviceability check on the stored lat/lng — catches company coverage change and the original location error. If now serviceable → straight into booking.

Best objective‑1 payoff for ~zero backend.

T3

Remote‑Config gated

managed config~60–80 LOC

Firebase RC (already wired) controls on/off, copy, channel, placement & the nudge threshold — layered on the local flag. No custom backend.

Kill/tune without a release — the train is dormant.

Ship: T2 as the core + T3’s RC kill‑switch as cheap insurance on a new production surface.
