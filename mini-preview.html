How tech enables this

The card is a self-gating composable: the landing screen mounts it unconditionally and it decides for itself whether to render. That means turning it on, tuning it or pulling it entirely is a config change, not a release.

1 · Where it lives

FileRole
feature/booking/ui/WiomTvMiniPreview.kt The card, its ExoPlayer lifecycle, and WiomTvReentryViewModel (gate, deep link, events)
feature/booking/ui/SplashHomeScreen.kt Hosts it — one line, a right-aligned Row in the content column with padding(bottom = 5.dp)
core/data/store/AnalyticsPrefs.kt hasVisitedWiomTv — the durable flag that qualifies a user
core/data/config/AppRemoteConfig.kt Remote Config schema, including the master switch

2 · Who it renders for — two locks

// WiomTvReentryViewModel — both must be true, no exceptions
val enabled: Boolean
    get() = remoteConfig.current.wiomTvReentryEnabled   // Remote Config, default false
            && prefs.hasVisitedWiomTv                  // this device opened Wiom TV before

The second lock is what makes this a re-entry surface rather than an ad. It latches at exactly one moment — when a user taps the Wiom TV band on the unserviceable screen and wiom.tv opens:

// WiomTvBandViewModel.logClicked()
prefs.hasVisitedWiomTv = true   // SharedPreferences — survives app kills and updates

A user who has never seen Wiom TV gets today's landing screen byte-for-byte. Debug builds render the card unconditionally so QA needs no Firebase and no prior visit.

3 · What plays

  • Channel comes from Remote Config (WIOM_TV_CHANNEL_NUM / _URL) — the same source the band uses, so both surfaces always show the same channel.
  • ExoPlayer (media3), muted, no controls, with a two-step fallback chain if the primary stream fails.
  • A poster covers the gap before the first frame and retires permanently once the stream renders, so a paused card never looks broken.
  • Stops after 30s and freezes on the last frame — these users have no Wiom net, so the stream costs them cellular.
  • Pauses when the app backgrounds, resumes on return, and the player is released when the screen leaves.

4 · What the tap does

https://wiom.tv/?ch=2&src=app_reentry_mini&ctid=__abc123def456
ParamCarriesWhy it matters
chThe channel currently playing in the card The user resumes on what they tapped, not a generic landing channel
srcapp_reentry_mini Separates re-entry traffic from first-contact traffic in the wiom.tv numbers
ctidCleverTap device id (omitted if blank) Joins an app user to their wiom.tv behaviour

⚠ One dependency on the wiom.tv side

wiom.tv already records every landing query param, so src and ctid work for attribution today. But nothing reads ch= yet — a user who taps a live Dangal TV card currently lands on the default channel instead. The ask is small: read ch in the boot path, resolve it against the channel list, tune to it, and fall back silently if it's unknown. Full spec in the PRD handoff contract.

5 · How to switch it on

Add the key to the customer_kotlin_app_config blob in Firebase Remote Config. No build, no release, effective on the next config fetch:

{
  "WIOM_TV_REENTRY_ENABLED": true,      // this card
  "WIOM_TV_BAND_ENABLED": true,         // the unserviceable band — enable first, it creates the audience
  "WIOM_TV_CHANNEL_NUM": 2,
  "WIOM_TV_CHANNEL_URL": "https://live-dangal.akamaized.net/liveabr/playlist.m3u8"
}
1 Merge — both off, production unchanged
→
2 wiom.tv ships ?ch=
→
3 Enable the band — it creates the audience
→
4 Enable this card

Order matters: this card has no audience until the band has been live long enough for users to have tapped it. Killing either is the same flag set back to false.

Note for tech — the build is currently 125 × 70

PR #352 ships the card at 125 × 70 dp, the size before this final step up. Locking the largest size means one constant change in WiomTvMiniPreview.kt (CARD_WIDTH = 153.dp, CARD_HEIGHT = 86.dp) — no layout rework, since the card is in the flow and the row simply reserves more height.
